# コアの堅牢性実装計画

## 調査結果

現在の実装はライフサイクル、所有者、チェックポイント、ジョブマニフェスト、
Wake receipt を複数の JSON ファイルで管理しています。Copier 更新との互換性は
ありますが、世代変更と所有者移譲は別々の書込みで、外部操作も一つの
トランザクションで記録されません。Supervisor と通知配送も分離した経路です。

## 採用する設計

- TOML、Git 管理対象の研究記録、ログ、成果物、Copier answers、設計資料は
  従来の場所に残します。
- 初期化完了後は `agents/runtime/adf.sqlite3` をランタイム状態の情報源にします。
- 移行完了までは既存 JSON を互換情報源として維持し、移行は明示的かつ再実行可能にします。
- ライフサイクル、所有者、世代、ジョブ、Wake receipt、外部操作意図を SQLite に保存します。
- 外部通信やプロセス操作中は DB トランザクションを保持しません。
- 移行中は互換 JSON をミラーとして残し、移行検証後のみ SQLite を正式な情報源にします。
- Codex CLI の検出と Queue 配送を Runtime Adapter に分離し、Codex がなくても
  ローカル状態とジョブ管理を可能な範囲で利用できます。
- GitHub の状態遷移とリポジトリ識別を明示的に検証します。

## 秩序移行と復旧

1. JSON の旧状態を検出し、スキーマを記録します。
2. 最初の移行前に SQLite のバックアップを作成します。
3. ライフサイクル、所有者、ジョブマニフェスト、Wake receipt を単一トランザクションで移行します。
4. 件数と代表的な状態を検証し、移行完了を記録します。
5. 移行の再実行は冪等で、完了済み操作を上書きしません。
6. Copier の更新でランタイム SQLite を配布対象または削除対象にしません。

## 完了条件

- 所有者とライフサイクルの競合が直列化され、原子的に更新される。
- 古い世代からライフサイクル変更や通知ができない。
- 停止処理や所有権移譲の途中異常終了を状態から復旧できる。
- Supervisor の異常終了後、ジョブが成功ではなく中断または不明になる。
- 通知意図と受領が永続化され、重複配送を防止する。
- GitHub の進捗変更は不正な遷移とリポジトリ不一致を拒否する。
- SQLite・JSON の移行成功、失敗復旧、再実行試験を持つ。
- CI が Python、SQLite、Copier、テンプレート、Skill を検証する。
